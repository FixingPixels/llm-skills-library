# Authoring Conventions

Shared conventions for skills in this framework. Read this before adding a new
skill (for example, a future `content-capability-analyst` or `multi-repo-analyst`)
so it drops into the existing structure without redesign.

## Skill layout

Each skill is a self-contained, independently installable folder:

```
skills/<skill-name>/
├── SKILL.md            # required — lean orchestrator
├── references/         # optional — read-on-demand detail
└── templates/          # optional — output skeletons, read only when writing
```

`SKILL.md` is loaded whenever the skill triggers, so keep it lean: the
what/when, a glance-able workflow, and pointers. Push detail and large output
skeletons into `references/` and `templates/` — the agent reads those only at
the step that needs them. This is progressive disclosure, and it is the point.

Keep references one level deep: link directly from `SKILL.md`. Do not nest a
reference that links to another reference.

## Frontmatter

```yaml
---
name: kebab-case-name        # lowercase, hyphens, max 64 chars
description: >-              # third person, what + when + trigger phrases
  <what the skill does>. Use when <trigger scenarios and phrasing>.
---
```

The `description` is how the skill is discovered, so make it specific. State
both what the skill produces and when the agent should reach for it, and include
the phrases a user would actually say.

## Evidence and sourcing

Every claim a skill emits must cite a named source — a file path or "git
history". No unsupported claims. If evidence is thin, say so; honesty beats
impressiveness.

## Controlled vocabularies

Keep assessments comparable across runs and skills by using fixed scales:

- **Signal Strength** (hard skills): `Core`, `Strong`, `Solid`, `Present`,
  `Exploratory`.
- **Assessment** (soft skills): `Exceptional`, `Thorough`, `Strong`, `Solid`,
  `Adequate`, `Sparse`, `Limited signal`.

## Portability

Skills must work across Claude.ai, Claude Code, and the API. Treat a shell as
optional: use it when present (e.g. `git log`) and degrade gracefully when it is
not. Do not assume a specific MCP server or tool exists. Prefer instructions
over bundled scripts unless an operation is genuinely fragile or deterministic.

## Generated-file markers

Skills that write files into the user's repo should mark them as generated, so
they are recognizable and safe to regenerate:

```markdown
<!-- Generated by code-reflection. Do not edit manually — re-run the analysis to update. -->
```
